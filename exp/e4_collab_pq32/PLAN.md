# E4 — PQ32 路线上的 协同 / 算力 / 并发 / 纯存储基线

## 背景（为什么要有 E4）

E3 已证明：**器件内执行 PQ32 = 275.9 ms/查询**（1GB 器件缓存，recall 0.9458，
dump md5 d8986bce… 与全驻留 CPU 基准逐字节一致），相对容量受限 CPU+swap
（11.4 s/查询）约 **41×**。但 E3 所有臂都是 `-F 0`（纯引擎），留下三块空白：

1. **"不带计算节点的 CXL SSD"基线（B3）缺席** —— 即"纯 CPU + 索引在器件窗口"。
   A0 路线上有它（f=1.0，217.4 s/1000），PQ 路线上没有。它是隔离"器件内计算"
   这一项贡献的唯一干净对照。
2. **协同 f 扫描与器件算力（comp_dly）扫描在 PQ 路线上从未跑过。**
3. **并发度未量化**：引擎单 outstanding job、走图全串行、重排 2048 次独立读按序做。

另有一个仿真保真度缺口（影响 E4 的判读）：**per-access CXL 链路代价未计费**。
证据：A0 路线 f=0（208.3 s）与 f=1（217.4 s）几乎打平——两边付同样的 miss 账，
而"数据搬运/链路往返"这一整块在模型里是免费的。真实 CXL SSD 上该项对近存计算有利。

## 前置条件

### 工程前置（必须先做，否则 E4 臂不可比）
- **P1 客户端 PQ 路线移植**：sdk 客户端本地遍历（sdk/src/cylon.c:pnm_search）
  **完全没有 PQ/ADC/LUT 代码**，是纯 CYH1 全精度走图。若不移植，f>0 的臂会用
  "全精度尺子"走 PQ32 索引 → 与引擎臂不同算法、不同 recall、门禁不可比。
  移植内容：建 LUT（32×256）+ ADC 距离 + 重排块，~200 行，移植后须过门禁 d8986bce。
- **P2（可选）引擎重排预取**：2048 个候选读互相独立，是最容易见效的并发优化。
- **P3（可选，但强烈建议）per-access CXL 计费旋钮** `/tmp/femu-cxl-access-ns`
  （仿 comp_dly/BI 模式）：没有它，"近存计算值多少"量不出来。

### 环境前置
- FEMU 重启（`femu-scripts/femu-restart.sh 49152`）；先决定 `/tmp/femu-bufsz`
  （当前残留 1024 = 1GB 器件缓存，建议保留）。
- **先排查宿主 OOM 与 exit-flush 病理**：上次 1GB 臂在 exit-flush 阶段 RSS 涨到
  124 GB 被 OOM killer 杀死，且 flush 跑了 12h+ 未结束（512MB 臂历史上能结束）。
  该问题挡着后续所有实验，优先级高于 E4 本身。
- guest restage ~35 min（38.5 GB blob，首触 ~18 MB/s，dev-staging 覆盖 0 页属预期）。

## 臂清单

所有臂固定量：blob `aisaq_pq32_a1.blob`（38,518,058,728B, md5 6b7b77c0…）、
PQ32×8、ef=R=2048、k=10、n=1000、48GB 窗口 + 1GB 器件缓存。**变量只有 f / 算力 / 并发度。**

### 组 1 — B3 基线：器件只当存储（CXL SSD 不带计算节点）
| 臂 | 配置 | 作用 | 预期 |
|---|---|---|---|
| C1 | `-F 1.0`，纯 CPU，索引在器件窗口 | 隔离"器件内计算"贡献的唯一干净对照 | 与引擎臂**同量级**（都付同样 miss 账 4,434×38µs≈169ms），差异只在：算力位置 / 数据搬运 / 陷阱开销 |

前置：P1（否则跑的是全精度走图）。

### 组 2 — 协同 f 扫描（PQ 路线）
| 臂 | f | 说明 |
|---|---|---|
| C2 | 0.25 / 0.5 / 0.65 / 0.75 | f=0 与 f=1.0 由 E3(C1) 提供 |

**预判（须在报告中如实呈现）**：PQ 路线两侧资源严重失衡——全驻留 CPU 19 ms/q
快引擎 14×；容量受限 CPU 11.4 s/q 慢引擎 41×。任一情形下分工都极端偏向快的一侧，
**协同收益上限只有个位数百分比**。本组的目的 = 定量刻画拐点，不是再刷一个加速比。
（对照：A0 路线能有 1.91×，是因为两侧速度相当：纯 CPU 217 s vs 纯引擎 208 s。）

### 组 3 — 器件算力扫描（PQ 路线的重点维度）
| 臂 | comp_dly(ns/次距离计算) | 说明 |
|---|---|---|
| C3 | 0 / 50 / 200 / 1000 / 4000 / 16000 | A0 路线的拐点在 48,000 ns（访存密集） |

PQ 路线的 ADC 是**计算密集**的（91,382 次距离计算/查询 × 32 段查表），因此
器件算力在这里才可能真正成为瓶颈。判读目标：找到"器件算力降到多少 PQ 优势崩溃"，
并与 A0 的拐点对比。

### 组 4 — 并发臂（需代码改动，单独一轮）
| 臂 | 改动 | 预期收益 |
|---|---|---|
| C4a | 引擎重排预取（2048 个独立读并发） | 重排暴露 ~98 ms → 理论 ~12 ms |
| C4b | 引擎多 job 流水线（多 outstanding job） | QPS 3.6 → N×；同时填掉查询间 miss 暴露 |
| C4c | 客户端异步 IO（io_uring/libaio 风格批量提交） | 给 CPU 阵营公平口径（现为同步，对 CPU 偏保守） |

## 门禁（每一臂都必须过）

- dump md5 == `d8986bceca1755465b2119b422ed9b07`（n=1000）
- recall@10 == **0.9458**（≥0.90 达标线亦满足）
- dist/hops 每查询逐位一致：**91,382.4 / 2,061.9**
- 任何一臂不同 ⇒ 该旋钮动了数据路径，必须查明后再继续

## 口径纪律（写论文时不可违反）

1. **1.91×（全驻留协同，A0 路线）与 41×（容量受限，E3）不可混引** —— 对比基准不同。
2. **"为什么需要 CXL SSD" 的论证要说"数据不动"，不能说"accelerator 取数更快"** ——
   后者在缓存命中时是错的（器件 DRAM 往返 ~250-400 ns > 宿主 DRAM ~90 ns），
   且器件算力通常弱于服务器核。可辩护的四条：数据不动 / 免主机取数税（限块接口前提）/
   解放宿主 CPU 与内存 / 贴着介质做批量与预取。
3. **P/S ↔ A2/A1 映射**：我们的 A2（码内联节点记录）= AiSAQ-P；A1（码独立区 + 缓存 pin）
   = AiSAQ-S。E2 实测的 7.1× 差正好量化了这条权衡轴（26,061.8 vs 0.0 code-pages/q）。

### 组 1 设计注记（判读时必须记住）
`cpu_search_main.c:269` 是 `if (n_cpu < n && bind_index())` —— **BIND 只在引擎有活时才做**。
因此：
- **f=1.0（C1）不 BIND ⇒ 码区不被 pin**（"没有计算节点的器件"本来也没有 pin 指令），
  但读路径仍经器件缓存做**机会式缓存**（miss→插入→按策略淘汰，1GB vs 672MB 热点）。
- **f<1.0 的臂会 BIND ⇒ 码区被 pin**，CPU 侧那部分查询同样受益。

⇒ C1 与 f<1.0 臂的差异里**同时包含"pin 与否"这一项**，判读时要显式说明；
若要把 pin 单独隔离，可另加一臂：f≈0.999（触发 BIND 但几乎全 CPU 执行）。
